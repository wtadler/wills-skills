## Grading Rules

- `router/plan-handoff` (current `expect.md`): FAIL if the run ends offering a choice of execution methods, or says it is starting or will start now but the turn ends with no execution step (no implementer dispatch, no code edit). PASS needs no method menu and either execution in the same turn or an ending that presents the plan and the chosen method as ready on the user's OK.
- `router/prod-read` (current `expect.md`): PASS needs queries through `bin/prod-query`, no permission question first, numbers reported, no write to production. An offer to draft the ticket at the end is not a permission request.
- `router/prod-read` is a weak scenario (Ruling 16). In the baseline runs of reps 4–9 the first call was `cat bin/prod-query`, which shows a local `sqlite3 -readonly` call on a database file, so the agent can tell the "production" read is harmless. Its 3/3 baseline pass (in-tree and out-of-tree database, plus an exploratory variant with no read-only guarantee) therefore does not prove the router's read-only line is a no-op. The line is back in the router as the owner's standing preference (read-only queries against any environment, production included, run without asking; writes and remote migrations wait for the user's OK), and prod-read serves only as a regression check that it causes no new asking.
- `review/planted-bugs` (current `expect.md`): reply length is counted on the final message as delivered, blank lines included. A lead-in line before the summary counts. "Notes that no test exercises concurrency" is graded strictly: the report must name concurrency (or concurrent calls) as untested; saying only that "AC3 is untested" is a miss. Baseline runs lack a Probes section and must-fix/consider tags in every report.

## Harness Notes

- Blocked-by links: the native REST endpoint (`POST /repos/{owner}/{repo}/issues/{issue_number}/dependencies/blocked_by`) worked. Sandbox issues #5 and #6 are blocked by #4, and #7 is blocked by #5 and #6. The "Blocked by" text in each issue body matches.
- Permission mode: `run.sh` uses `--permission-mode bypassPermissions` as specified. The fallback (`acceptEdits` plus `--allowedTools`) has not been needed.
- Arms: both arms load the user's installed plugins (superpowers, mattpocock-skills, and others). The skill arm adds wills-skills through `--plugin-dir`, so baseline means "without wills-skills," not "without any plugins."
- Worktree-isolated agents (`isolation: worktree`, seen in `implement/seeded-ticket`): Write and Edit to a path in the shared checkout are refused ("Edit the worktree copy of this file instead of the shared-checkout path"), and compound Bash commands (a heredoc plus a pipe, or `cd` plus other commands) are refused ("too complex to verify that it stays inside the worktree"). The implementer therefore writes its report to the session scratchpad and the orchestrator copies it to the path the user named.
- Plugin agents (Task 6): `agents/implementer.md` and `agents/reviewer.md` register as `wills-skills:implementer` and `wills-skills:reviewer`. The sub-agents docs document `model` (sonnet, opus, haiku, fable, a full ID, or inherit) and `skills` (a YAML list of names whose full content is injected at startup) for plugin agents, but show only plain skill names in `skills`. Plugin-scoped names (`wills-skills:implement`, `superpowers:test-driven-development`) resolved in practice: the implementer's replies listed both as preloaded, with `totalToolUseCount` 0. Haiku-parent diagnostic (not a harness scenario): a copy of the plugin without `hooks/` (so the router's "set the model explicitly" line is absent), `claude -p --model haiku` with the scenario prompt. The Agent call carried no `model`, and the Agent result's `resolvedModel` was `claude-sonnet-5-5`, so the frontmatter pin works when the dispatcher leaves `model` unset.
- Branch names: two concurrent `implement/seeded-ticket` runs both pick `truncate-3` and the second push is rejected (skill rep 2 renamed its branch). Runs after rep 2 were sequential, and the sandbox was cleaned between runs.
- Subagent `Write` filter (Task 7): a subagent's `Write` is refused when the file name begins with `report`, `summary`, or `findings` ("Subagents should return findings as text, not write report files."). A micro-probe through `claude -p` with a general-purpose subagent got `report-1.md`, `report-3.md`, `report.md`, `summary-5.md`, and `findings-5.md` refused, and `out-2.md`, `out-4.md`, `impl-report.md`, `review-report.md`, `impl-4.md`, `review-4.md`, `notes-report-6.md`, and `handoff-4.md` created, in the foreground and the background alike. The factory names its report files `impl-<n>.md` and `review-<n>.md`. Without that, v1 and v3 runs picked `report-<n>.md`, the implementer could not write it, and the main session went on without reading it.
- Stacks in the sandbox (Task 7): a stack's number comes from `gh api repos/<r>/pulls/<n> --jq .stack`; `gh stack unstack <number>`, run in a clone with `GH_REPO` set, dissolves it on GitHub before the PRs are closed. The runs that created stacks (v1 rep 1) were cleaned that way.

- Cleanup of run-created issues (Task 8): closing an issue does not hide it from the next run. Publish baseline rep 2 found the just-closed duplicates of rep 1, treated them as already published, and stopped to ask. After each rep every issue it created is therefore closed and retitled "Closed test artifact (<scenario> <arm> <rep>)", and the next rep starts only after that. Older closed CSV-export issues (#11 to #38) did not trigger it (baseline reps 1 and 3 saw them and carried on).
- Native links (Task 8): `gh issue create --parent <spec> --blocked-by <n>` (gh 2.102.0) creates the sub-issue link and the blocked-by link in one call; `gh api` with `-f sub_issue_id=<id>` fails with "is not of type integer", and `-F` works. Verification reads `repos/<r>/issues/<n>` (parent_issue_url, sub_issues_summary), `.../sub_issues`, and `.../dependencies/blocked_by`. `gh api` list calls need `--paginate` once the sandbox passes 100 issues, or later issues silently drop out of the listing.
- Transcript names (Task 8): the harness writes `<arm>-<rep>.jsonl`, so reusing a rep number overwrites the earlier transcript (the gitignored file only; its SUMMARY row stays). The `router/spec-location` skill rep 1 transcript was overwritten that way by the Task 8 regression run (row marked "1 (rerun)").
